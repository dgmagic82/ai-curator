# Структурированный вывод: JSON и проверка ответа модели

## Зачем нужен структурированный вывод
Пока ответ модели читает человек, свободный текст подходит. Но как только ответ передаётся программе (таблице, боту, CRM, следующему шагу автоматизации), нужен предсказуемый формат. Программа не поймёт фразу «тональность, пожалуй, скорее негативная». Ей нужно поле со значением из заранее известного списка. Самый распространённый формат для этого JSON: текстовая запись объектов с полями и значениями. Его понимают почти все языки программирования и no-code инструменты, а структуру JSON легко описать и проверить автоматически.

## Как просить JSON в промпте
Чтобы модель стабильно возвращала JSON, в промпте нужно описать структуру как можно точнее: какие поля, какого типа, какие значения допустимы, что делать при нехватке данных. Хорошо работает образец ответа и явный запрет на текст вне JSON.

```
Извлеки данные из заявки клиента. Верни только JSON
без пояснений и без markdown-разметки, строго по схеме:

{
  "name": строка или null,
  "phone": строка или null,
  "course": одно из "промптинг", "rag", "агенты", "другое",
  "urgent": true или false
}

Если поле не указано в заявке, ставь null.
Не придумывай данные, которых нет в тексте.

Заявка: «Здравствуйте, меня зовут Ольга, хочу на курс по RAG,
перезвоните сегодня, пожалуйста».
```

Перечень допустимых значений (enum) особенно важен: без него модель может написать «RAG-курс», «курс RAG» и «rag» в разных ответах, и программа сочтёт их разными категориями.

## Встроенные режимы структурированного вывода
Многие API языковых моделей предлагают специальные режимы помимо обычного промпта. Есть JSON-режим, который гарантирует синтаксически корректный JSON. Есть режимы структурированного вывода, где разработчик передаёт JSON Schema (формальное описание полей и типов), и ответ обязан ей соответствовать. Близкий механизм используется при вызове функций, о нём рассказывает лекция 4-1. Набор таких режимов и их названия различаются у разных провайдеров и моделей, поэтому перед использованием сверяйтесь с документацией конкретного API. Даже при включённом режиме смысл полей проверяет не синтаксис, а ваш код или человек.

## Проверка ответа модели
Ответ модели нельзя передавать дальше без проверки, даже если обычно он правильный. Проверка идёт в несколько уровней.

Синтаксис: строка разбирается как JSON. Типичные сбои: текст до или после JSON, обёртка в markdown-блок, обрезанный ответ из-за лимита токенов.

Схема: есть все обязательные поля, типы верные, значения входят в разрешённый список. Для этого удобны готовые валидаторы JSON Schema или библиотеки вроде Pydantic в Python.

Смысл: значения правдоподобны и согласованы с входом. Например, телефон действительно встречается в тексте заявки.

Если проверка не прошла, есть три стратегии: повторить запрос, повторить запрос с текстом ошибки валидатора («поле course содержит недопустимое значение, исправь»), либо отправить случай человеку. Число повторов стоит ограничить, чтобы не попасть в бесконечный цикл.

## Типичные ошибки со структурированным выводом
Схема описана словами расплывчато, без типов и списка значений. Нет правила для отсутствующих данных, и модель заполняет поля выдумкой. Поле со свободным текстом вроде «комментарий» без ограничения длины раздувает ответ. Ответ разбирается «на глаз» без валидатора, и редкие сбои обнаруживаются уже в рабочей таблице. Схема меняется в коде, а промпт остаётся старым. Хорошая практика: хранить схему в одном месте и подставлять её в промпт автоматически.

## Главное из лекции
- Структурированный вывод нужен, когда ответ модели читает программа.
- В промпте описывайте поля, типы, допустимые значения и правило для пропусков.
- Встроенные JSON-режимы API различаются у провайдеров, проверяйте документацию.
- Проверяйте синтаксис, схему и смысл ответа перед тем, как передать его дальше.
- При ошибке повторяйте запрос с текстом ошибки и ограничивайте число повторов.
