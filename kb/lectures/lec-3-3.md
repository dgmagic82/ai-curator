# Как оценить качество RAG

## Почему RAG оценивают по частям
RAG-система состоит из двух звеньев: поиска (retrieval) и генерации ответа. Плохой ответ может появиться в любом из них. Поиск мог не найти нужный фрагмент, и тогда модели просто не из чего ответить. Или поиск нашёл всё верно, но модель проигнорировала фрагмент, исказила его или добавила выдумку. Если оценивать только итоговый ответ, непонятно, что чинить: разбиение, эмбеддинги, промпт или модель. Поэтому качество RAG проверяют раздельно: сначала поиск, потом генерацию, и только затем систему целиком.

## Эталонный набор вопросов
Основа любой оценки RAG: набор тестовых вопросов с ожидаемыми ответами. Для каждого вопроса записывают, в каком документе или фрагменте лежит ответ (это нужно для оценки поиска) и каким должен быть правильный ответ по смыслу (для оценки генерации). Набор должен включать простые вопросы, вопросы с перефразированием (другими словами, чем в документе), вопросы, ответ на которые собирается из двух фрагментов, и вопросы, ответа на которые в базе нет. Последняя группа часто забывается, хотя именно на ней видно, умеет ли система честно сказать «не знаю». Для учебного проекта достаточно 15–30 вопросов, но собранных вручную и продуманно.

## Метрики поиска
Для поиска используют метрики, которые сравнивают найденные фрагменты с ожидаемыми.

Recall@k (полнота на k): доля вопросов, для которых нужный документ попал в первые k результатов поиска. Если на 20 вопросов из 25 нужный документ оказался в топ-5, recall@5 равен 0,8.

Precision@k (точность на k): какая доля из k найденных фрагментов действительно релевантна вопросу.

MRR (средний обратный ранг): учитывает, на каком месте стоит первый правильный результат. Правильный фрагмент на первом месте даёт 1, на втором 1/2, на третьем 1/3, затем значения усредняют по вопросам.

Для RAG обычно важнее всего recall@k: если нужного фрагмента нет в выдаче, генерация уже не спасёт ситуацию. Эти метрики считаются автоматически, без участия модели, поэтому их удобно прогонять после каждого изменения разбиения или модели эмбеддингов.

## Метрики генерации
Ответ модели оценивают по нескольким качествам. Обоснованность (faithfulness, groundedness): все утверждения ответа подтверждаются найденными фрагментами, выдумки нет. Релевантность ответа: ответ отвечает именно на заданный вопрос. Правильность: ответ совпадает по смыслу с эталоном. Корректный отказ: на вопросы без ответа в базе система говорит, что информации нет, а не сочиняет. Оценивать генерацию может человек по заранее заданной шкале или другая модель в роли судьи (LLM-as-a-judge). Судью тоже нужно проверять: выборочно сравнивать его оценки с оценками человека.

Пример промпта для модели-судьи:

```
Ты проверяешь ответ ассистента на обоснованность.
Даны фрагменты источника и ответ.
Для каждого утверждения в ответе определи, подтверждается
ли оно фрагментами. Верни JSON:
{"unsupported_claims": [список неподтверждённых утверждений],
 "verdict": "обоснован" или "есть выдумка"}

Фрагменты: {фрагменты}
Ответ: {ответ}
```

## Как пользоваться результатами оценки
Метрики полезны, только когда их сравнивают. Зафиксируйте исходные значения на эталонном наборе, затем меняйте одну вещь (размер фрагмента, k, модель эмбеддингов, промпт) и прогоняйте оценку снова. Помимо цифр, читайте конкретные провалы: часто один разбор неудачного вопроса показывает системную причину, например таблицу, разрезанную при разбиении. Помните, что на маленьком наборе разница в один-два вопроса может быть случайной, поэтому не делайте далеко идущих выводов из небольших колебаний.

## Главное из лекции
- RAG оценивают раздельно: поиск, генерацию и систему целиком.
- Основа оценки: эталонный набор вопросов с ожидаемыми источниками и ответами.
- Для поиска считают recall@k, precision@k и MRR, главная из них обычно recall@k.
- Для генерации проверяют обоснованность, релевантность, правильность и корректный отказ.
- Меняйте одну вещь за раз и сравнивайте метрики с исходными значениями.
